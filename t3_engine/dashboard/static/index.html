Runs on OpenRouter (openrouter.ai/api/v1), ~openai/gpt-astra-latest by default. If the server has a key configured you can leave the field below empty; otherwise paste your own — it is sent to your own backend for one request at a time and never stored server-side (see ai_advisor/advisor.py). The model can give a second opinion and propose a wave count; it can never override the rule-based engine's accept/reject decision.

API key

Saved only in this browser (localStorage), never sent anywhere except your own backend.

Model

One id, or several separated by commas — the router walks the list and uses the first that answers. Worth doing: a free model behind a shared GPU pool returns "service temporarily overloaded" a good fraction of the time, and a list turns that into a non-event instead of a failed run. Format vendor/model, optionally with a :free suffix. Editable because catalogues change; if a call comes back 404 the id no longer resolves — paste the current one here, no redeploy needed. The AI Analyst needs a model that supports tool calling; one that doesn't will answer in prose and submit nothing.

API base URL

This build cannot reach the host to confirm it, so it stays editable: if every call returns 404 no matter which model you pick, the path is wrong. Pasting the full endpoint works too; it won't be doubled up.

Timeout

Seconds to wait for one answer. Free router models queue behind other traffic and reasoning models think before emitting a first token, so a slow reply is normal — a read timeout means the connection worked and the model was still busy, which is a different problem from a wrong URL.

Reasoning effort

max is the default now: the best answer the model can give, and by far the slowest. The analyst makes one call per step, so the cost multiplies — and since a run is a background job you can close the tab on, the slowness is no longer a reason to hold back. Drop to medium if you want a quick look, or pick Not sent if you point the endpoint at a model that has never heard of this parameter: such a model answers 400 rather than ignoring it.

Model thinking

Sent as OpenRouter's own reasoning: {enabled, effort}. On by default now that the model is paid — it was off while the free models sat behind a shared GPU pool, where thinking meant minutes before the first byte; on a paid model thinking is the reason to use it, and an Elliott count is exactly the kind of work it helps. The model's reasoning is also carried across steps (reasoning_details passed back unmodified), so the agent picks up where it left off instead of re-thinking from scratch on every step. "Do not send" is for a model that has never heard of the field and answers 400 rather than ignoring it.

Check the connection

Diagnose first lists the catalogue (GET /models) — that needs the key and the same URL but runs no model at all. If it answers, the key, endpoint and network are fine by construction and any slowness belongs to the model or its queue. Then it looks at the chat endpoint raw: status, headers, whether the body is really a stream, and the timing of each phase.
One tiny request. A wrong key, a wrong URL, a dead model id and a model that just queues all look the same from here — this tells them apart before you wait on a long run.

Ask the model about the current setup

Signal quality (kumo-relational)

A different kind of model: it takes a relational table and returns a probability per row, with no text output and no tool calling — so it cannot label waves or replace the chat model. What it can answer is the one question the engine already has the table for: given how a setup scored on its eight components, how often did setups like it actually end green? Strictly advisory — it never gates a trade, moves a stop or edits a count. A model fitted to a few dozen of the engine's own past trades is a hint, not an edge.

AI wave labelling

The model proposes a count across the whole loaded history — the one thing the deterministic engine deliberately won't do, since it only anchors on recent pivots. The model only ever names pivot indices; the server recomputes those pivots itself and re-checks existence, order, contiguity, alternation, causality and the hard Elliott rules before anything is drawn. A mathematically impossible wave comes back rejected, with the rule it broke.
A clean chart and an agent, nothing else. This tab loads the candles and hands the model no markup — no pivots, no BOS/CHoCH, no scenarios, no Fibonacci — then lets it work the chart with real tools: list the swings at any degree, measure legs, compute Fibonacci levels, and test a count against this server's rule engine before committing to it. It is told the Elliott rulebook (hard rules vs. guidelines, impulses, diagonals, zigzags, flats, triangles, combinations) and asked to work top-down, oldest structure first.
Separate chart on purpose: a model shown an existing markup tends to agree with it. Here the two counts stay comparable instead of superimposed. Every structure it submits is still re-validated server-side — anything that breaks a hard rule is listed below as rejected, never drawn.

Run the analyst

One model call per step. Measured over nine saved runs of the same charts: at 10 steps coverage averaged 84% and one chart came back only 41% labelled; at 15–16 it averaged 97.5% with the worst case 95%, and the number of validated structures roughly doubled (4.4 → 10.3 per chart). Every 15–16 step run also spent its entire budget, so the ceiling — not the chart — was still what stopped it. Default is 24 for that reason. A run is a background job you can close the tab on, so the only thing a long budget costs is tokens, and the panel reports exactly how many.

Conversation

Everything the model said, thought and called, in order — so "why did it stop at step N" has an answer instead of a guess. Thinking is shown where the model streams it separately.
A full count of the whole history, every timeframe, made by the rule engine rather than by a model — so it costs nothing to run and nothing to re-run. Build pulls 1500 bars each of 5m, 15m, 1h and 4h from Bybit, files them so they survive a deploy, then searches every structure that could start at every swing and keeps only the ones the hard rules accept. Waves 1, 3 and 5 are then subdivided into their own i–ii–iii–iv–v at a finer deviation, by the same rules. Fleet

Counts 5m, 15m, 1h and 4h and reconciles them into one opinion. A count from a single timeframe answers a question nobody asked: a five-wave advance on 5m inside a 4h correction is a bounce, and only looking at both says so.
Timeframes whose data has not moved are read from cache, not recounted — a 4h chart produces one new candle every four hours, and a full run is a dozen model calls. Freshness is decided by the newest candle the saved analysis saw, never by a clock. The result names what was reused and what was recomputed, so the saving is visible rather than claimed.
