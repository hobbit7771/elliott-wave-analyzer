# OrderFlow Terminal

Браузерный терминал анализа потока ордеров на реальных данных Binance: свечной график с инструментами
рисования, heatmap ликвидности, DOM, footprint, CVD/дельта, Volume Profile / TPO, детекторы (крупные уровни,
предполагаемые айсберги, поглощение, подозрение на спуфинг, кластеры, sweep, stop-run, дисбаланс, вакуум
ликвидности), статические дневные уровни поддержки/сопротивления, replay, серверные paper-trading и алерты.

**Только анализ, paper-trading и бэктест — кода отправки реальных ордеров нет.**

- Сайт: https://orderflow-terminal-yjsg.onrender.com (Render Free, Frankfurt)
- История: Supabase Free (Postgres + Storage), проект в `eu-central-1`
- Код: папка `orderflow-terminal/` репозитория `hobbit7771/elliott-wave-analyzer`, ветка `eliot-top-1`

<a id="arch"></a>
## 2. Архитектура

```
Binance WS (/public, /market) ─┐
Binance REST (snapshot, backfill, сверка, дневные свечи) ─┤
                               ▼
                 worker_threads: по одному на инструмент (лимит кучи 128 МБ)
   BookSync → OrderBook → FlowClassifier → детекторы → heat / candles / footprint
        │                         │
        │                  PersistWriter ──► Supabase Postgres (схема oft, роль oft_app)
        │                         └────────► Edge Function oft-archive ──► приватный bucket (L2-блоки)
        ▼
   main thread: Hub (WS к браузерам), REST API, PaperService, AlertService, RetentionService, статические уровни
        ▼
   Браузер: Vite + lightweight-charts v5, Canvas, Web Worker для декодирования потока
```

- Локальный `node:sqlite` — только горячий кэш (сырой heatmap 45 мин, сделки 2 ч) на диске проекта.
  Диск Render Free эфемерный, поэтому источник истины — Supabase: после перезапуска история читается оттуда.
- «Ворота сигналов»: новые сигналы выдаются, только когда стакан синхронизирован и свежий, а поток сделок жив
  (тишина > 15 с закрывает ворота). При разрыве — ресинхронизация и запись интервала разрыва; данные
  никогда не интерполируются.
- Свечи: закрытые бары — CLOSED, формирующийся — LIVE. Если REST биржи недоступен, график строится из
  сохранённых закрытых 1m-свечей с явной пометкой.

<a id="sources"></a>
## 3. Источники данных и ограничения

- **Binance L2** — суммарный объём на цене, без order ID, владельца и очереди. Отдельные ордера не видны.
- Стакан приходит пакетами по 100 мс: разделение «исполнено / снято» внутри пакета — оценка.
- **История стакана** есть только с момента начала записи: биржа её не отдаёт.
- **Общий исходящий IP Render** (74.220.51.139) периодически получает от Binance REST бан 418 из-за чужого
  трафика. WebSocket работает; снапшоты стакана проходят со второй-третьей попытки; сверка с REST, OI и
  бэкфилл временно недоступны — это видно на вкладке «Источники». Параметры инструментов и последние
  статические уровни хранятся в Supabase и доступны во время бана. Пока бан действует, сервер **не отправляет**
  к этому хосту ни одного REST-запроса (Binance продлевает бан за запросы во время него); после 429 — пауза
  по `Retry-After`. Свечи 15m–1D при недоступном REST строятся из кэша биржевых свечей в Supabase
  (`oft.klines`, год 15m и дневки) плюс записанные 1m.
- **Основной источник — Bybit** (по умолчанию в интерфейсе и в постоянной записи: BTCUSDT, ETHUSDT). REST
  Bybit с Render работает без банов; Binance остаётся доступен в списке и открывается по запросу.
- **Bybit** (USDT-перпетуалы, v5): стакан 200 уровней на сторону (снимок приходит в потоке, дальше
  дельты с update id +1; разрыв → переподключение и новый снимок), сделки без числовых id (их
  непрерывность не проверяется), догрузка сделок по REST ограничена 1000 последними.
- **CME / Nasdaq** — только через лицензированные платные фиды. Данные Binance никогда не смешиваются с CME.
- **CFD / OTC (XAUUSD, BRXUSD)** — централизованного стакана нет; не предлагается. Binance XAUUSDT — собственный
  стакан Binance, а не COMEX.

<a id="detectors"></a>
## 4. Детекторы и честная семантика

Детерминированная математика по WebSocket-данным. **Score 0–100 — эвристика, а не калиброванная вероятность.**
Каждое событие объясняет, что измерено и что предположено.

- **«Предполагаемый айсберг»** — исполнено больше, чем было видно, при этом видимый объём не уменьшался
  (≥ 2 скрытых пополнения, скрытое ≥ 20% исполненного). «Исполнено − первоначально видимое» — **не точный
  размер скрытого остатка**: то же дают новые независимые заявки и агрегация потока.
- **«Признаки пополнения уровня»** — объём восстанавливался видимыми добавлениями после исполнений.
- **«Поглощение»** — сильная агрессия в уровень без продвижения цены.
- **«Подозрение на спуфинг»** — только подозрение: крупный уровень ≤ 0,2% от mid, к которому цена
  приблизилась, снят почти без исполнения; не чаще раза в минуту на сторону.
- **«Снятие крупной ликвидности»** — снятый объём больше порога крупного уровня, рядом с рынком; раз в минуту на сторону.
- **Крупный уровень** — держится ≥ 10 с; порог динамический: `max(2% глубины стороны, P97 объёмов уровней) × ATR-множитель [1; 1,5]`.
- **Кластеры** — держатся ≥ 30 с, только 3 крупнейших на сторону. **Вакуум** — раз в минуту на сторону.
- Версия алгоритма пишется в каждое событие (`algo_version`, сейчас `oft-detectors-5`); история статусов
  хранится отдельно: `/api/events?asOf=` показывает состояние на момент T без заглядывания в будущее.

<a id="levels"></a>
## 5. Уровни на графике и heatmap

**Статические дневные уровни (синие сплошные линии, до 4).** Уровни, где проторговался большой объём и
цена многократно отскакивала или с трудом пробивала:

1. 365 закрытых дневных свечей; развороты (фракталы ±2 дня) группируются в пределах 0,35 × ATR(14).
2. Для каждого уровня: отскоки (тень дошла до уровня, закрытие осталось по сторону подхода), дни у уровня
   перед пробоем, объём около уровня.
3. Объём около уровня — **оценка по дневным OHLCV** (объём дня равномерно по его диапазону): дневного профиля
   объёма Binance не отдаёт.
4. Нужно ≥ 2 отскоков; берутся 4 сильнейших с расстоянием ≥ 1,5 × ATR.
5. Пересчёт раз в 6 часов; последний результат хранится в Supabase. Слой «Статические уровни D1» в «Слоях».

**Живые уровни (до N, по умолчанию 6, переключатель «Уровней»).** Тонкие пунктирные линии, мелкая подпись у
правого края, подписи не накладываются. **Фиолетовая линия с меткой на шкале** — важный уровень: ≥ 2× порога
крупного и держится ≥ 60 с (или пополнялся), действующий предполагаемый айсберг / поглощение со score ≥ 70,
либо протестированный кластер. Полные списки — на вкладке «Сигналы».

**Heatmap.** Единая палитра интенсивности (тёмно-синий → голубой → зелёный → жёлтый → оранжевый → красный →
белый); между снимками стакана нет чёрных полос, настоящие разрывы заштрихованы; события — маленькие значки,
короткая подпись только при score ≥ 85.

<a id="setups"></a>
## 5a. Сильные уровни D1 и входы по правилам Герчика (✅ LONG / ✅ SHORT)

**Один движок для истории, повтора и live** (`src/core/levelEngine/gerchik.ts`, `GerchikEngine.step(bar)`):
на вход — только ЗАКРЫТЫЕ 15-минутные свечи; D1 строится из них; уровни D1 пересчитываются только после
закрытия дневной свечи. Ордер выставляется на закрытии свечи и может исполниться только на следующих
свечах; если свеча задела и стоп, и цель — считается стоп. **Комиссии Bybit (maker 0,02%, taker 0,055%) и
проскальзывание стопа вычитаются из каждого результата в R.**

**Уровни D1 (до 10, `dailyLevels.ts`)** — тот же метод, что и у одобренной разметки: реакция в ATR,
CHOP/пила → **CHOPPED**, настоящий пробой → **BROKEN**, смена роли → **FLIPPED**, сила 0–100 с разбором.

**Модели входа (правила Герчика):**
- **Отбой (БСУ → БПУ1 → БПУ2).** Сильный уровень D1 — это БСУ. Закрытая свеча, коснувшаяся уровня
  «тик в тик» (в пределах люфта) с правильной стороны и закрывшаяся за ним, — БПУ1. Лимитный ордер на
  уровень ± люфт исполняется, когда цена возвращается (БПУ2). Ордер снимается, если цена ушла на 2 стопа.
- **Пробой с поджатием.** Несколько маленьких свечей прижаты к уровню с растущими минимумами (для шорта —
  падающими максимумами) → стоп-ордер за уровнем + люфт.
- **Ложный пробой** реализован, но на сайте выключен: отдельно он дал отрицательный результат.
- **Стоп** = 0,5 × ATR(D1) за уровнем, **люфт** = 20% стопа, **цель** = 3 стопа (3:1).
- **Только по тренду D1** (закрытие выше SMA50 и SMA растёт → только LONG; наоборот → только SHORT).
  Это убирает входы против движения («шорт на росте»).
- **Запас хода:** если следующий сильный уровень ближе цели 3:1 — входа нет.
- Направление определяется на **каждой** свече по стороне закрытия относительно уровня. В прежнем движке
  оно фиксировалось в начале подхода: после прохода уровня насквозь и ретеста с другой стороны сигнал мог
  быть в неправильную сторону.

**Как выбраны параметры и что получилось (честно).** Данные: 14 монет Bybit (BTC, ETH, SOL, XRP, DOGE,
BNB, ADA, LINK, AVAX, SUI, UNI, INJ, HYPE, XPL), год 15m, с комиссиями. Скрипты: `scripts/experiments/`.
- Короткий стоп «по учебнику» (10–20% ATR) на 15m убыточен: комиссии съедают ~0,25R на сделку, шум выбивает
  стоп. Лучше 0,4–1,0 ATR.
- Фильтр тренда D1 — самый устойчивый параметр; свежие уровни (максимумы/минимумы 1–5 последних дней)
  дают втрое больше сделок, но результат ≈ 0; сильные исторические уровни — лучше.
- Подбор параметров под период **не переносится** на следующий: у 800 вариантов корреляция результата
  TRAIN (первые 6 мес.) и VALIDATION (следующие 3 мес.) ≈ 0. Поэтому параметры **фиксированы для всех
  монет** и не подгоняются под монету.
- Итог выбранной конфигурации на 14 монетах: **128 сделок за год, +0,17R на сделку, 33% прибыльных,
  PF 1,25**; по периодам: первые 6 мес. +0,42R (48 сделок), следующие 3 мес. −0,04R (23), последние 3 мес.
  +0,05R (57). Прежний движок на тех же данных: +0,02R за год, −0,38R и −0,24R в последних периодах.
- **Статистически это не доказанное преимущество**: стандартная ошибка ≈ ±0,15R на сделку, а последние
  9 месяцев около нуля. Сделок мало (≈ 9 в год на монету), серия до 8 убытков подряд. Это инструмент
  разметки и анализа, не торговая рекомендация.

**Карточка сетапа** (нажатие на ✅): уровень и его сила, модель (отбой / пробой), сколько ждал ордер,
вход, стоп, цель, следующий сильный уровень, reason codes (модель, стоп в % ATR, RR, по тренду/против),
выборка (TRAIN / VALIDATION / OOS / LIVE) и фактический результат после комиссий (R, MFE, MAE).

**Техники Линды Рашке («Street Smarts», L. B. Raschke & L. A. Connors, 1995)** — `src/core/levelEngine/raschke.ts`,
на тех же закрытых 15m-свечах, «день» = сутки UTC, те же правила исполнения и комиссии. Реализованы сетапы
книги: Turtle Soup, Turtle Soup +1, 80-20, Momentum Pinball (LBR/RSI), ID/NR4, Holy Grail (ADX(14) > 30,
первый откат к EMA20). Сам текст книги не использовался (авторское право); правила — по опубликованным
описаниям сетапов. Проверка на тех же 14 монетах за год, с комиссиями:

| Turtle Soup +1 | 112 | +0,22 | +0,26 | +0,53 | −0,20 | −0,09 |

Перебор выходов и фильтров (выбор только по первым 6 месяцам): у TS+1, 80-20 и ID/NR4 на первом периоде
плюс почти у всех вариантов и минус у **всех** вариантов на следующем — это смена режима рынка, не
преимущество. Устойчиво держится только Holy Grail на D1 с параметрами книги (ADX > 30), и условие силы тренда
(ADX) улучшает входы Герчика. На сайте включено:
- уровни Герчика + условие Рашке «ADX(14) ≥ 20 и DI в сторону сделки» (порог выбран по первым 6 мес.);
- Holy Grail (D1, ADX > 30, первый откат к EMA20, стоп-ордер выше бара отката, цель — прежний экстремум,
  до 10 дней).

Итог на 14 монетах, с комиссиями: **138 сделок, +0,29R на сделку, PF 1,50** (Герчик+ADX: 91 сделка, +0,23R;
Holy Grail: 47, +0,39R). По периодам: 1–6 мес. +0,46R (69), 7–9 мес. +0,58R (16), **последние 3 мес. −0,04R
(53)**. Лучше прежней версии (+0,17R), но последние 3 месяца — около нуля, поэтому это по-прежнему не
доказанное преимущество. Остальные сетапы Рашке есть в коде и в `scripts/experiments/`, на сайте выключены.

| Тайм-серийный моментум (знак прошлой доходности → будущая) | лучший t = 1,8 (20 → 20 дней) | слабый трендовый эффект, на грани значимости |
| Автокорреляция \|r\| (кластеры волатильности) | 0,18 / 0,09 / 0,05 (лаги 1/5/20) | волатильность предсказуема — надёжнее всего управлять размером риска |
| Средняя корреляция монет | 0,60 → ≈ 1,6 независимых монеты из 17 | сделки по разным монетам — почти одна ставка на рынок; значимость «по числу монет» завышена |
| Эксцесс дневных доходностей | ≈ 6 (у нормального 0) | тяжёлые хвосты: редкие большие движения |

Отсюда модель: мелкие частые убытки по стопу в единицах ATR (размер позиции обратно пропорционален
волатильности) в обмен на редкие длинные тренды тяжёлого хвоста; фильтр рыночного фактора (тренд BTC).

**Трендовая модель (`trend.ts`, система пробоя канала Дончиана / «черепахи»).** Проверка на 5 годах дневных
данных (`dbt.py`, приказы только по закрытым дням, стоп раньше цели, комиссии Bybit, фандинг лонгов ≈ 0,03 %/день):
- без подбора: пробой 20/выход 10 — +0,18R на сделку (1 162 сделки), 55/20 — +0,13R; лонги +0,31…+0,43R, шорты ≈ −0,05R;
- Holy Grail Рашке на 5 годах — **−0,10R** (196 сделок): его плюс на одном году был случайностью, с сайта убран;
- семейство из 112 вариантов (вход 20/40/55/100 дней, выход 10/20, стоп 2/3 ATR, только лонг, фильтр BTC, фильтр
  эффективности Кауфмана): **все 112 положительны** за весь период; скользящий walk-forward (выбор по 2 прошлым
  годам, торговля следующие 6 месяцев, 06.2023–09.2026): Шарп **1,21**, +193R, макс. просадка 58R; «купить и держать»
  корзину с тем же риском: Шарп 0,80, просадка 128R; блочный бутстреп p = 0,042; с поправкой на 112 попыток
  (deflated Sharpe) вероятность настоящего преимущества 0,36 — строго говоря не доказано;
- выбрана конфигурация плато, лучшая в обоих подпериодах: вход на 20-дневном максимуме, стоп 3 ATR(20),
  выход по 10-дневному минимуму, только лонг, не против тренда BTC — 455 сделок, +0,47R, Шарп 1,12
  (2021–23: 0,41; 2023–26: 1,39), просадка 55R;
- последний год для трендовой торговли плохой (полугодия −8R, −6R, +12R); 15m-движок и дневной симулятор на нём
  совпадают (−0,03R и −0,07R);
- ограничения: монеты — сегодняшние «выжившие» (завышает лонги), эффективных независимых монет ≈ 1,6.

**Идея уровней Герчика на 5 годах** (тот же движок на дневных свечах, 2022–2026): без фильтров −0,06R (211),
со строгим трендом −0,09R, со строгим трендом и ADX ≥ 20 **+0,06R** (70; 2025–26: +0,24 и +0,22). Фильтры силы
тренда переводят её из минуса примерно в ноль.

**Что работает на сайте:** тренд (пробой канала) + уровни Герчика с ADX ≥ 20 (`siteEngine.ts`); движок каждой
монеты получает закрытые дневки BTC как рыночный фактор. Последний год на 15m (14 монет, с комиссиями):
168 сделок, +0,11R на сделку, PF 1,21 (отбой +0,24R, тренд −0,03R); по периодам +0,02 / +0,08 / +0,24R.
Предыдущая версия (с Holy Grail) на этом году выглядела лучше (+0,29R), но не выдержала 5 лет — выбрано
то, что устойчиво на длинной истории.

Прежний движок (`setupEngine.ts`: затухание объёма → касание → реакция объёмом → micro BOS) оставлен в коде
и тестах для сравнения.

**Watchlist (вкладка «Уровни»):** монеты выбирает владелец; для каждой — цена, ближайшая сильная
поддержка и сопротивление, расстояние в % и ATR, сила уровня и состояние автомата.

**История свечей** кэшируется в Supabase (`oft.klines`, миграция `0003`): год 15m-свечей скачивается один
раз, дальше — только хвост; «дыры» после оборванной загрузки докачиваются. Бэктест идёт в отдельном
потоке (`analysisWorker`), пересчёт раз в 12 ч или по кнопке.

<a id="volume"></a>
## 5b. Объём относительно нормы инструмента

Всплеск объёма считается только относительно нормального объёма этого же инструмента:
`volumeRatio = объём интервала / скользящая медиана` и `volumeZScore = (объём − среднее) / σ`
(σ ограничена снизу 20% среднего, чтобы почти ровное окно не давало огромный z). Параметры калибруемые
(`burst`: интервал 10 с, окно 360 интервалов, `ratioMin` 1,5, `zMin` 2, режим `and`/`or`, пауза 30 с).
По умолчанию режим `and` (оба условия): на 10-секундных интервалах `or` с порогом 1,5 срабатывает слишком часто;
переключается в настройках детекторов. Абсолютный объём нигде не используется.

<a id="history"></a>
## 6. История и архив в Supabase

| Данные | Где | Срок хранения (по умолчанию) |
|---|---|---|
| Тайлы heatmap 10 с | `oft.heat_tiles` | 2 дня |
| Тайлы heatmap 60 с | `oft.heat_tiles` | 30 дней |
| Значимые события и история их статусов | `oft.events`, `oft.event_status` | 10 дней |
| Закрытые 1m-свечи | `oft.candles_1m` | 365 дней |
| Исходные L2-блоки (точный replay) | bucket `oft-archive`, манифесты `oft.archives` | 12 часов |
| Разрывы и покрытие | `oft.gaps`, `oft.coverage` | вместе с данными |
| Параметры инструментов, статические уровни, настройки | `oft.instruments`, `oft.settings` | постоянно |

- В историю пишутся только значимые события (в живом интерфейсе видны все): крупный уровень — score ≥ 85 и
  размер ≥ 2× порога; снятие ликвидности — уровня ≥ 2× порога; кластеры, дисбаланс, вакуум — score ≥ 75;
  редкие события (айсберги, поглощение, sweep, stop-run, спуфинг, дивергенция, всплеск объёма) — все.
- Блок архива: snapshot стакана в полосе ±2% + все diffs + сделки за 5 минут, gzip, sha256. Манифест `pending`
  до загрузки и `final` после проверки; незавершённые после сбоя доводятся или удаляются с записью разрыва.
- `/api/archive/book?t=` восстанавливает точный стакан (в пределах полосы) на момент t.
- Квоты: бюджет БД 400 МБ, Storage 850 МБ. При превышении БД сначала прореживается журнал событий, затем
  приостанавливаются тайлы 10 с; при превышении Storage — архивные блоки. Видно в диагностике и в логах `OFT_STORAGE`.
- Удаление истории — только владельцем, только явного интервала, с подтверждением.

<a id="security"></a>
## 7. Безопасность

- Схема `oft` не публикуется через Supabase API; RLS на всех таблицах; у `anon`/`authenticated` прав нет.
- Сервер подключается ролью `oft_app` с минимальными правами. Ключ `service_role` есть только внутри Edge
  Function `oft-archive`.
- Доступ к архиву — через Edge Function с ключом `x-oft-key`, сверяемым с `oft.secrets`. Анонимной записи и
  удаления нет.
- Изменяющие действия (paper, алерты, настройки, объекты графика, удаление истории, диагностика) требуют токена
  владельца (`x-oft-owner` = `OWNER_TOKEN`). Токен вводится на вкладке «Источники» и хранится только в браузере.
- Секреты (`OFT_DB_PASSWORD`, `OFT_ARCHIVE_KEY`, `OWNER_TOKEN`) — только в секретах Render; в репозитории,
  фронтенде и логах их нет.
- В production сервер ходит только на официальные хосты Binance / Supabase / Databento.

## 8. Локальный запуск


<a id="supabase"></a>
## 9. Настройка Supabase

1. Проект Free в регионе `eu-central-1`.
2. Миграции из `supabase/migrations/` по порядку (`0001_oft_init.sql`, `0002_oft_app_role.sql`).
3. Роль приложения и ключ архива (значения придумайте сами и храните только в секретах Render):
   ```sql
   create role oft_app login password '<пароль>';
   insert into oft.secrets (k, v) values ('archive_key', '<ключ архива>');
   ```
4. Edge Function `supabase/functions/oft-archive` (проверка JWT выключена: доступ по `x-oft-key`).

<a id="render"></a>
## 10. Деплой на Render Free

Web Service, регион **Frankfurt** (Binance Futures отвечает 451 на IP из США), план Free.

- Build: `npm ci --include=dev && npm run build`, Start: `npm start`, Health check: `/api/health`.
  Если проект в подпапке — Root Directory `orderflow-terminal`.
- Переменные — `render.yaml` и `.env.example`. Важные: `DB_PATH=data/orderflow.sqlite` (кэш на диске, не в
  `/tmp`), `MALLOC_ARENA_MAX=2`, `NODE_OPTIONS=--max-old-space-size=384`, `MAX_SESSIONS=2`. Секреты
  `OFT_DB_PASSWORD`, `OFT_ARCHIVE_KEY`, `OWNER_TOKEN`, `SUPABASE_PROJECT_REF` — вручную во вкладке Environment.
- Render Free засыпает после ~15 минут без входящих запросов. Искусственный keep-alive не используется: время
  сна записывается как разрыв данных.

| Метрика | Значение |
|---|---|
| CPU | 0,09–0,10 из 0,15 в среднем за 5 мин (до 0,145 при загрузке истории) |

Найдено и исправлено по логам `OFT_REQ` / `OFT_MEM`: процесс перезапускался (00:24, 00:28, 00:53 UTC),
когда несколько запросов истории heatmap шли одновременно (+80…+181 МБ кучи на запрос). Теперь чтение

Ограничения, которые остаются:
- CPU Free-плана — главное ограничение. Если трёх записей окажется много, Bybit можно убрать из постоянной

- REST Binance с общего IP Render периодически получает бан 418. Живой поток от этого не зависит, но
  загрузка годовой истории 15m для бэктеста (ETHUSDT) и свечи из REST временно недоступны; недостающее
  дозагружается после окончания бана (кэш `oft.klines`).
- Загрузка сделок для footprint/профиля (`/api/trades`, до 150 000 сделок) при нехватке CPU занимает до 2 мин.

<a id="notclaimed"></a>
## 13. Что сознательно не заявляется

- «Видеть» скрытые ордера: только предположение со score.
- Доказательство спуфинга: только подозрение.
- MBO, место в очереди, отдельные ордера: Binance публикует только агрегированные уровни.
- История стакана до начала записи.
- Точный дневной профиль объёма: объём у статических уровней — оценка по OHLCV.
- Данные CME/Nasdaq без платного фида и вашего разрешения; стакан CFD.
- Реальная торговля; push-уведомления при закрытом браузере.

```bash
git subtree split --prefix=orderflow-terminal -b orderflow-terminal-only
```
